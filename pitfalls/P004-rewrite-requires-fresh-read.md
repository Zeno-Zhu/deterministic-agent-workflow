# P004 · 跨轮次重写同一个文件被拒：`File has not been read yet`

> 冷存件：**默认不读**。只有当 `INDEX.md` 中本行匹配到当前现象时才打开。

## 现象

在**同一轮**里已经读过某文件，下一轮想整体重写它时，`Write` 直接报错：

```text
Error: File has not been read yet: .../references/code-engineering.md.
Read it first before writing to it.
```

明明上一轮刚读过全文 —— 症状是「我读过了，它却说没读」。

## 根因

「已读」状态**不跨轮次保留**（按会话内最近一次读取判定）。
跨轮次做**整体重写**（`Write` 覆盖）时，工具会重新要求先 `Read`。
局部替换（`Edit`）走的是另一条路径，用 `old_string` 直接匹配磁盘内容，所以不受影响 ——
这也是为什么「先 Edit 过好几次、再 Write 就突然被拒」看起来毫无规律。

## 解决方案

跨轮次要整体重写时，**先补一次读取**（哪怕只读前几行）再 `Write`：

```text
Read <path>  (limit 12 就够，目的只是刷新「已读」状态)
Write <path> (完整内容)
```

改局部就用 `Edit`，不要为了「保险」整体重写 —— 整体重写还会丢掉并行 `Edit` 与
CRLF 归一化带来的稳定性。

## 为什么不是别的方案

- ❌ 遇错就改用 `Edit` 逐段打补丁拆掉重写 —— 对 400 行级的重构，逐段 `Edit` 的匹配失败率更高；
- ❌ 换个文件名写、再改名 —— 破坏 git 历史与引用，代价远大于多读一次。

## 复现条件

- 环境：本宿主（WorkBuddy 的文件工具）
- 触发：跨对话轮次 + 目标文件是**已存在**文件 + 用 `Write` 整体覆盖
- 概率：必现

## 通用性判定

- 判断：`✅ 一类操作`
- 「换个项目还成立吗」自检：成立 —— **任何「读状态按轮次管理」的工具都有这个边界**。
  归纳成一句：**跨轮次重写已存在文件前，先刷新一次「已读」；局部改动优先用替换式编辑。**
