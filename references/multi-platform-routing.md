# 多平台 / 多版本：中控与渠道线 VNext

> 本文件是「**同一件事有多个平台能干时，skill 怎么拆、怎么调度**」的唯一权威。
> 主方法见 `SKILL.md` 的「多平台与多版本」节；契约见 `references/vnext-contracts.md` 第 12 节。
> 与 `file-governance.md` 的分工：那边管**一个 skill 内部**的文件，这边管**多个 skill 之间**的边界。

## 0. 问题

同一件事往往有多个平台能干，且**约束完全不同**。真实差异长这样：

| 差异面 | 例子 |
|---|---|
| 参数上限 | 参考图上限 9 张 vs 10 张 |
| 时长口径 | 恒 30 秒 vs 整数 4–15 秒 |
| 输入能力 | 能不能传参考音频（一条不能传） |
| 计费模型 | 按次 / 按秒 / 按小时 |
| 调用协议 | 字段名不同（`reference_images` vs 把引用写进 prompt） |
| 资源生命周期 | 参考图 URL 只活 1 小时、且不去重 |
| 流程步骤 | 一条要"先传图床再提交"，另一条可直接复用 |
| 失败模式 | 上游把假报错伪装成正式错误码 |

把这些塞进**一个** skill，必然出现三件事：

1. `SKILL.md` 里长出 if/else 分支，越写越大；
2. AI 每次都要读**全部平台**的约束 —— 烧 token，且关键规则被淹；
3. ★ **参数串味** —— 把 A 平台的经验套到 B 平台，报错还查不出来。

**结论：按渠道拆成独立 skill，用一个中控做路由。**

---

## 1. 拆分判据：满足任一就拆

| 判据 | 说明 |
|---|---|
| 模型名不同 | 模型标识不同 = 不同的东西 |
| 参数约束不同 | 上限、时长、画幅、必填字段 |
| 计费模型不同 | 按次 / 按秒 / 按时 |
| 调用协议不同 | 端点、字段名、鉴权方式 |
| 流程步骤不同 | 多一步或少一步（先传图床、能不能带音频） |
| 资源生命周期不同 | URL TTL、是否去重 |
| 失败模式不同 | 失败信号的形态与处置 |

**反判据（不该拆）**：只是同一协议下的**参数取值不同**（换分辨率、换画幅、换语气档）→ 那是 `config/`，不是新 skill。

---

## 2. 结构：一个中控 + N 条渠道线（互不嵌套）

```text
skills/
├── <domain>-creation          # ★ 中控（router）—— 只做路由
├── <domain>-<channel-a>       # 渠道线 A —— 自包含
├── <domain>-<channel-b>       # 渠道线 B —— 自包含
└── <domain>-<channel-c>       # 渠道线 C —— 自包含
```

**渠道线是独立 skill，不嵌在中控目录里。**
理由：AI 按需加载 —— 只有被路由到的那一条会进上下文，其余**一个字都不读**。这就是省 token 的全部机制。

---

## 3. 中控 skill 的硬规则

中控只做三件事，多一件都算污染：

1. **辨识**用户要哪条渠道；
2. **只加载那一条**渠道线，其余一律不读；
3. **声明用了哪条**。

必须有的内容：

- **路由表**（唯一权威，放 `references/routing-table.md`）
- **默认渠道** + 未点名时的判定规则
- **公共约定**（所有渠道共用、且**不会因渠道而异**的部分）
- 切换渠道时的**改动清单**（读哪个协议文档、加载哪个 skill）

**严禁内联**：任何渠道的**参数上限、计费、字段名、模型名、报错特征、坑**。
出现下列任一 = 结构错误：

- 中控 `SKILL.md` 里出现渠道专属数值（`9 张` / `按秒` / `每小时 ¥3`）
- 中控 `SKILL.md` 里写了某渠道的报错特征或坑
- 中控的 `Load First` 列了**各渠道 skill**（应该只列**路由表**）

### 路由表格式（固定列，勿改）

```markdown
| 渠道 | 触发词 | 子 skill | 关键差异（一句话） | 协议文档 |
|---|---|---|---|---|
| A | 点名 A / 模型名拼写 | `<domain>-channel-a` | 按次计费、时长固定、不能传音频 | `<path>` |
```

- 「关键差异」列的作用是**帮 AI 选**，不是**替 AI 执行** —— 所以写**能力形态**，不写数值。
- 「子 skill」列必须是**真实存在的同级 skill 名**（死路由会被校验脚本判错）。

## 4. 渠道 skill 的硬规则

- **自包含**：协议文档、参数表、坑、脚本全在自己的目录里。
- ★ **禁止跨渠道引用**：不得写「和 B 渠道一样，只是……」。
  理由：B 渠道的参数改了，这条路引用**不会知道**，会静默失效。
- `description` 必须覆盖用户**实际会说的**触发词：正式名、口语简称、旧名、平台名、模型名的各种拼写。
- `references/` 里必须有**协议文档**：模型标识、端点、鉴权、字段、计费、上限、失败信号。
- 坑**只记本渠道的**；跨渠道的共性问题属于中控或域级通用 skill。

---

## 5. 多版本：同平台多版本 = 多个渠道 skill

**硬规则：同一平台的不同版本各建一个渠道 skill，不用 if/else 分支。**

- 命名：`<domain>-<platform><major>`（例：`...-jimeng20` / `...-jimeng25`）
- 弃用版本：`description` 标 `[已弃用/历史]`，路由表标 `历史`；中控**默认不选**，除非用户点名。
- **未来加版本 = 加一个 skill + 路由表加一行，不动任何存量 skill。**
  ← 这是拆分最大的收益：新平台不会逼你回去改老 skill。

---

## 6. 代码侧：API 中控三件套

Skill 层拆了，**代码层必须跟着拆**，否则参数照样串味。

```text
registry（数据）   → 每个平台/版本一行：模型名、端点、鉴权、计费、上限、能力开关、失败信号
client（实现）     → 每个平台一个 client，只认自己那套字段
scheduler（决策）  → 选路 + 限流 + 重试 + 计费闸
```

硬规则：

1. ★ **业务代码里禁止出现模型名字符串。** 模型名只允许出现在 registry。换模型 = 改 registry 一行。
2. **能力查询必须走 registry**，不要在业务里写 `if 平台 == X`。
3. **选路顺序固定**：`能力是否满足 → 成本 → 可用性`。能力不满足直接淘汰，**不参与比价**。
4. **计费闸**：提交前先算预估成本并过闸；没有成本估算的批量提交视为缺陷。
5. ★ **协议文档按渠道分割**：`<渠道>/<协议>.md`。
   **禁止一份文档写多个平台** —— 一份文档混装是参数串味的头号来源。
6. **失败信号也进 registry**（哪条是"假失败"、哪条可捞回、哪条只能重跑）。

---

## 7. 调度纪律

- **一次任务只跑一条渠道线**，禁止并行两条 —— 参数会串味。
- 用户点名 → 直连该渠道；**未点名 → 走默认渠道，并在回复里显式声明用了哪条**。
- 跨渠道比价 → 只读各渠道的**能力 + 计费摘要**，不读全文。
- 换渠道 = **重跑**「写参数 → 自检 → 提交」整条链，**不假定上一条链的产物能直接复用**。
- 云端资源（实例 / 图床 URL）**按渠道分别记账**，别跨渠道复用生命周期。

---

## 8. 拆分落地清单

- [ ] 中控 `SKILL.md` 里**没有**任何渠道专属数值 / 报错特征 / 坑
- [ ] 中控 `Load First` 只列路由表，**不列渠道 skill**
- [ ] 路由表每行的「子 skill」真实存在（校验脚本会查死路由）
- [ ] 每个渠道 skill 自包含，**没有跨渠道引用**
- [ ] 默认渠道已声明；未点名时会**显式说出来**
- [ ] 代码里没有硬编码模型名；模型名只在 registry
- [ ] 协议文档**一渠道一份**，没有混装
- [ ] 弃用渠道已标 `历史`，默认不被选中
