# 代码工程纪律 VNext

> 本文件是「**产出 Skill 里涉及代码时，代码怎么写**」的唯一权威。
> 与另两份的分工：
> - `file-governance.md` 管**文件放哪、怎么死**（位置与生命周期）；
> - `multi-platform-routing.md` 管**跨平台边界**（拆不拆、选哪条）；
> - 本文件管**单条链路内部的代码纪律**（分类、复用、分层、任务生命周期、JSON、日志、测试、输出）。
>
> 只要产出物里包含代码，`SKILL.md` 的 Load First 就要求读本文件。

## 0. 总原则

1. **先分类问题，再决定处理力度。** 禁止不分类就直接改代码。
2. 代码不一定最短，但必须**稳定、清晰、可维护**。
3. **不过度设计**：不为"看起来高级"引入不必要的架构、安全机制、复杂抽象或超前设计。
4. **局部问题局部修**；一旦触及数据流、任务流、共享模块、跨文件接口、状态管理、调度、补偿、日志体系、项目隔离 —— **必须全局思考、系统性处理**。
5. **改一个文件不等于改完**：必须检查并同步所有相关文件、配置、调用链、类型、常量、日志、测试入口。
6. 可配置的一律参数化，**不要把本该可变的东西硬编码**。
7. ★ **业务代码单文件 ≤ 300 行**；重复逻辑多或职责混杂就必须抽公共模块。
   （配置文件、声明文件、纯数据文件可合理例外 —— 但要**在 `ARCHITECTURE.md` 里写明例外与理由**。）
8. **复用优先**：项目里已有相近的稳定流程时，先分析它为什么稳，禁止重复造轮子。
9. **重视日志**：关键步骤、状态变化、异常原因、补偿动作、跳过原因都要有清晰日志。
10. **能真跑就必须真跑**；跑不了就明确说出缺的环境/依赖/密钥/权限，**禁止假装测试过**。
11. 为测试临时写的测试代码、打印、调试脚本，**验证后必须删除或隔离**（隔离规则见 `file-governance.md` §4）。
12. 输出优先给**最终可落地方案**，不长篇空谈。
13. **避免过度编程**：核心闭环完整可用的前提下，不主动引入微服务、复杂权限/消息队列/调度平台/多租户/审计/风控。
14. 简单问题用简单方案，复杂问题做系统治理，**禁止一刀切**。
15. ★ **关键结构化数据默认用 JSON** 组织，便于存储、回放、排查、复用和下游调用。

## 1. 先做问题分类

收到需求先判类型（可多选），**分完类再决定是局部修还是系统治**：

`A` 语法/导入/拼写/明显报错 ｜ `B` 局部逻辑错误 ｜ `C` 跨文件调用或数据结构不一致 ｜
`D` API 调用、异步任务、队列、轮询、下载、重试、恢复 ｜ `E` 架构整理、公共模块抽取、重复逻辑收敛 ｜
`F` 配置、参数、项目隔离、日志体系 ｜ `G` 性能或并发控制 ｜ `H` 结果缺失、任务漏下载、任务状态与文件不一致 ｜
`I` 提示词读取、切换、格式一致性、下游兼容 ｜ `J` 其他

### 默认走局部修复

语法错、import 错、变量/函数名拼错、单个参数传错、单个判断写反、局部空值/类型/格式问题、
单个函数返回值处理错、单页面/单接口的小范围逻辑错。

### 必须系统性处理（任一命中）

- 数据结构 / 任务状态 / 配置格式发生变化
- 一个问题可能影响多个文件、模块或调用链
- 涉及 API 提交、轮询、下载、重试、恢复、去重、补偿、对账
- 多种能力混合调度（文本 / 生图 / 视频）
- 涉及项目隔离、任务记录、重复执行过滤
- 公共逻辑重复，需要抽模块
- **"提交成功但结果没落盘 / 没下载 / 被忽略"**
- **"表面报错只是后续表现，根因在前面的状态或流程"**
- 提示词文件读取、切换机制、输出格式变更、下游兼容性
- 多条流程共享同一类提示词或同一类返回结构

## 2. 复用优先与稳定流程

已有可稳定运行的相近流程时，**先分析它为什么稳定**：

- 输入结构是否稳定
- 状态流转是否清晰
- 下载与恢复是否完整
- 日志是否足够
- 异常处理是否成熟

然后按此顺序选择：**直接复用 → 同模式复写 → 小范围抽象 → 局部修改**。

★ **禁止为了"更优雅 / 更先进 / 更统一"贸然推翻现有稳定方案。**

真要重构或抽象，必须写明四件事：**原方案哪里不够 / 为什么需要抽象 / 新方案如何兼容旧流程 / 风险点在哪**。

---

## 3. 项目结构与公共模块

动手前先设计目录，明确每层的职责、存放内容与边界，至少分清：

路由·接口层 ｜ 业务流程层 ｜ 第三方调用层 ｜ 数据结构层 ｜ 提示词管理层 ｜ 日志与记录层 ｜ 配置层 ｜ 工具函数层

**≥2 条流程会复用的能力，必须抽成公共模块**，例如：
API 调用、响应解析、JSON 清洗、下载逻辑、日志记录、提示词读取、提示词变量填充、状态更新、对账与恢复。

**禁止**把提示词内容、复杂 JSON 模板、大段系统提示词硬编码进多个业务文件重复维护。

### 配置与代码分离

| 配置类型 | 放哪 |
|---|---|
| 少量简单配置 | 常量文件 |
| 普通项目配置 | `.json` / `.yaml` / `.ini` |
| **敏感配置** | 环境变量或独立配置文件，**绝不硬编码进业务代码** |

路径、模型名、API 地址、并发参数、轮询间隔、下载目录、日志级别 —— 全部配置化。

## 4. 提示词文件管理

### 4.1 基本规则

1. 提示词默认用 `.txt` 存放，**不散写在业务代码里**。
2. 程序必须能自动读取 `.txt` 提示词。
3. 支持按分类管理，并支持用户切换。
4. 分类至少区分：`system prompts` / `user prompts` / `output format spec` / `examples` / `fallback·repair prompts`。
5. 同类提示词统一命名规范，便于查找、替换、版本管理。

### 4.2 ★ 输出格式一致性（最重要）

1. **必须单独维护一份「提示词最终输出格式说明文件」**，定义这类提示词最终应输出什么结构。
2. 程序读提示词时，应同时知道：当前用途 / 预期输出格式 / 是否有变量占位符 / 是否要求严格 JSON。
3. ★ **只要最终输出结构一致，提示词文案可以自由迭代，不应影响下游。**
4. 一旦提示词更新导致**输出结构变化**，必须同步改：输出格式说明文件 → 响应解析 → JSON 校验 → 下游消费逻辑。
5. ★ **优先保证"输出结构稳定"，其次才是文案优化。**

### 4.3 变量与切换

1. 占位符规则**全局统一**，禁止每个项目各写一套。
2. 切换提示词时必须校验：必要变量是否齐全 / 输出格式说明是否匹配 / 当前流程是否允许切换。
3. 分类错误、文件缺失、变量缺失、格式说明不匹配 —— **必须明确报错，不允许静默失败**。

---

## 5. 数据与 JSON 契约

1. 关键数据默认 JSON 结构化，便于存储、传递、校验、复用。
2. 只要有 API 返回文本，**必须在提示词或接口契约里提前定义要哪些 JSON 字段**。
3. 收到 API 返回**不能假设它是干净 JSON**，必须解析 + 清洗。
4. 解析优先级（固定顺序）：

```text
要求模型直接返回纯 JSON
  → 去掉代码块包裹、说明文字、无关前后缀
    → 提取最可能的 JSON 主体
      → 解析后做字段校验
        → 仍失败才兜底截取（第一个 { 到最后一个 }）
```

5. ★ **"取第一个 `{` 到最后一个 `}`" 只是兜底，不得当主方案长期依赖。**
6. 关键 JSON 至少具备 `message` / `data` 这类通用意识。
7. 多流程共享的返回结构**必须定义统一字段规范**，不得各写各的。
8. 解析失败必须记录：**原始返回 / 清洗结果 / 失败原因**。

## 6. API 任务生命周期与对账

涉及 API 或异步任务时，默认按这套设计。**跨平台边界（选哪条、怎么拆）见 `multi-platform-routing.md`；本节的"怎么跑一条链路"归这里。**

### 6.1 调度骨架

1. 用**统一调度核心**（scheduler / dispatch brain）协调任务生命周期。
2. 可按能力拆调用中心（文本 / 生图 / 视频），各自负责：提交参数组装、提交频率控制、状态查询、结果下载、错误分类。
3. ★ **默认「错峰提交 + 后台并行等待」**：不一次性猛推 → 按**参数化**间隔逐个提交 → 已提交的进后台监控 → 全部提交完后继续轮询至全部完成或到策略终点。
4. API 调用逻辑**集中封装**，供应商差异不得散落到业务文件里。
5. 未来可能接多个平台时，**预留统一入口**（见 `multi-platform-routing.md` §6）。

### 6.2 任务状态机

必须明确区分（不要只有"成功/失败"两态）：

```text
pending → submitted → queued → running/generating → success
                                      ↓
                    download_pending → downloaded
                                      ↓
        failed / rejected / insufficient_balance / timeout / lost_result
```

### 6.3 ★ 失败分型，不统一重试

| 失败类型 | 处置 |
|---|---|
| 仍在生成 | 继续等待 |
| 平台无余额 | **暂停流程并提示用户**（不要硬重试烧钱） |
| 内容审核失败 | 记日志 + 标原因，**不盲目重试** |
| 网络问题 / 超时 | 按策略重试 |
| **提交成功但文件未落地** | 补查 → 补下载 → 对账 |

### 6.4 记账与防重复

所有任务都要记录：`task_id` / 项目归属 / 提交时间 / 状态变化 / 结果路径 / 失败原因。

★ 程序重跑时，**必须先读历史记录**，按项目维度过滤、判断、核对 —— 避免交叉污染与重复执行。

### 6.5 ★ 对账是正式流程

1. 核对已提交的 `task_id`；
2. 核对本地是否已有对应结果文件；
3. 没有文件时继续判断：**未完成 / 未下载 / 下载失败 / 平台无结果 / 记录丢失**。

**对账与恢复必须是正式流程的一部分，不能只靠人工排查。**

## 7. 日志内容清单

位置、保留策略、默认不读 —— 见 `file-governance.md` §5。**本节只管"该记什么"。**

必须覆盖：任务提交 ｜ 状态轮询 ｜ 下载开始/成功/失败 ｜ **跳过原因** ｜ **重试原因** ｜
审核失败原因 ｜ 余额不足 ｜ **对账结果** ｜ JSON 解析失败 ｜ 提示词读取/切换/校验失败。

- 初期调试日志可更详细，后期可降级，但**不能没有**。
- 不同项目的数据、状态记录、日志**必须隔离**，禁止互相污染。
- 重要日志必须能关联 `task_id` / `request_id` / `project_id`。
- 涉及 API 的流程建议同时记：发送内容 / 接收内容 / 清洗结果 / 最终解析结果。
- 含敏感内容时支持脱敏或分级记录。
- ★ **失败原因要标准化分类** —— 否则每次报错文案都不同，后期无法统计。

## 8. 测试与验证

1. **能运行就运行**，不要只做纸面分析。
2. 涉及付费 API 时，**先做最小成本测试**再扩大执行。
3. 无法真实调用外部 API 时，至少做：本地逻辑 / 状态流转 / 假数据或模拟响应 /
   下载与恢复逻辑 / JSON 清洗与解析 / 提示词读取与切换。
4. ★ **不允许声称"已测试"但实际没运行。**
5. ★ 临时测试脚本、临时打印、临时调试代码，**最终交付必须删除或隔离**（`file-governance.md` §4）。
6. 交付前先自检核心流程：能否启动 / 主流程是否跑通 / 关键状态是否正常流转 /
   关键数据是否正常传递 / 关键异常分支是否有明确表现。
7. 修 bug 时（语法小问题除外）必须同时检查：输入数据 / 上下游字段传递 / 状态流转 /
   复用模块影响面 / 下载·恢复·对账逻辑 / 提示词输出结构兼容性。

## 9. 输出协议（代码类任务按此顺序）

```text
1. 需求理解
2. 问题分类
3. 局部修复还是系统性处理（+ 理由）
4. 根因分析（多维度）
5. 改动方案
6. 需要修改的文件及关联影响
7. 具体代码实现
8. 实际测试步骤
9. 测试结果
10. 清理说明（删了哪些临时测试代码）
11. 后续可优化项（只列必要项，不泛泛而谈）
```

不能直接改代码时，**也必须按同样顺序给出分析与实施方案**。

> 与 `SKILL.md`「输出与验证」的关系：那边是**改 Skill 本身**时的三部分输出（原内容问题 / 修改原则 / 最终文件）；
> 这边是**写代码**时的十一部分输出。两套并存，按任务类型选。

---

## 10. 禁止事项

1. 禁止不分类问题就直接改代码。
2. 禁止只修表面报错，不追查真实根因。
3. 禁止只改当前文件，不检查关联调用链。
4. 禁止为了显得专业而过度设计。
5. 禁止重复造轮子。
6. **禁止假装测试过。**
7. 禁止把提示词散落硬编码到多个业务文件里。
8. 禁止在输出结构变更时，不同步调整解析与下游逻辑。
9. 禁止让任务记录、日志、状态在多个项目之间交叉污染。
10. **禁止把兜底策略当主流程长期依赖。**
11. 禁止把密钥 / 令牌硬编码进业务代码（`scripts/validate-skill.py` 会扫）。
12. 禁止让业务代码单文件无限膨胀（> 300 行就该看要不要抽模块）。
